# Piik 可继续借鉴的优化：第二轮源码对照

审查日期：2026-09-27，Asia/Shanghai。范围：本机 Piik 快照与 Roomcast beta.7 当前实现。本轮只新增分析文档，没有修改应用、测试、构建或发布。实施记录见 [时间戳](时间戳记录/PIIK-二次审查-20260927.md)。

## 结论与顺序

优先考虑**停止操作的整体取消时限**和**补全故障阶段记录**；其次是**控制消息入口与积压限制**、**真实画面进展观测**。**稳定成员身份与刷新恢复**有直接体验收益，但涉及成员协议，需要独立设计。**共享编码分组**只适合作为性能实验。

这里的优先级是根据当前源码和用户反复遇到的异常作出的判断，不是已复现新故障的严重性评级。Piik 未运行、未安装依赖，也无法确认该无 Git 元数据快照对应的上游版本。

动态邀请处理、独立成员存活检查、第一次点击现有离开入口就强制清理、逐项资源释放已经在 beta.7 落地，不重复列作新功能。

## 1. 停止操作：总时限覆盖排队和全部清理步骤

**Piik 的事实**：原生采集 `Stream.Close()` 在等待控制锁、写停止命令之前，先启动 1 秒取消计时；采集命令通过 `CommandContext` 绑定取消。可借鉴的是“先建立取消边界，再执行可能等待的操作”，不是照抄 1 秒这个数字，也不是声称 Piik 的所有退出路径都有硬保证。

**Roomcast 的事实**：已经有 OBS 单次请求超时、WebSocket 代次隔离、所属 OBS 进程树强制终止；窗口 ×/Alt+F4 已直接结束桌面主进程。`runObsCaptureOperation()` 把停止排在此前操作之后；`ObsFixedFpsEngine.close()` 依次等待虚拟相机、采集输入、探针、统计、控制连接，之后才结束 OBS。请求默认 8 秒，各阶段有自己的预算，但整个停止请求没有覆盖排队的统一预算。

**建议的最小落点**：停止被接受时，立即作废本次采集操作和排队的旧启动结果，在等待队列之前建立整体清理预算。保留正常资源释放；预算耗尽时只终止该操作持有的 Roomcast 子进程。复用现有 captureId/engine 对象匹配，旧清理不得关闭后来新建的采集。用户继续使用现有停止/离开/×，不增加第二个“强制退出”按钮。窗口直接退出行为保持。

**验收条件**：旧操作永不回应、清理每一步都拖延、停止后立刻新开采集三种情况，都能恢复后续操作，且旧停止不能杀掉新采集。主线程自身同步阻塞时 JavaScript 计时器不能执行，不能把该方案宣称为解决所有未知异常。

## 2. 故障记录：把失败发生在哪一步留下来

**Piik 的事实**：诊断模块写结构化日志，保留受限大小和轮转备份，可以导出；对令牌、密码、邀请片段等脱敏，并用摘要标识关联同一连接。其 SafeText 明确不承诺隐藏网络地址和系统路径，不能整套照搬后声称“完全匿名”。

**Roomcast 的事实**：已经有本地、受限大小、字段白名单的 P2P 网络统计，以及 VDO 发布统计；不能说没有诊断。现有 P2P 入口是 `window.roomcastP2pDiagnostics`。本轮检查到的这些统计主要描述媒体连接，不是统一的邀请解析→鉴权→入房→媒体首帧→离开清理时间线。

**建议的最小落点**：在已有诊断基础上增加受限的阶段事件与耗时，使用本次操作编号关联；明确记录取消、超时、过期回调被忽略。仅允许版本、阶段、状态码、耗时等必要字段，排除完整邀请、密钥、SDP、原始 ICE 地址；优先字段白名单，文本脱敏作为补充。诊断采集失败不得阻塞业务。可在既有设置/诊断入口提供本地导出，不自动上传。

**实际收益**：下一次手机失败时，能区分“未完成鉴权”“控制连接正常但没有首帧”“停止已发出但采集清理未结束”，减少仅凭一条最终提示猜测原因。它不能直接修复跨网络连不上。

**验收条件**：环形记录达到上限后有界；测试邀请密钥等不进入输出；坏统计/文件错误不影响加入和退出；导出包含明确版本及操作时间。

## 3. 控制消息：特殊回包也要有检查和连接归属

**Piik 的事实**：协议解码拒绝未知字段和错误类型；信令有接收大小限制、发送积压预算。发送预算在入队前看当前积压，可能超出一个消息大小，不能当作绝对字节上限。

**Roomcast 的事实**：普通访客请求已有事件白名单、入房权限、频率限制，图片块限制 48 KiB；其他请求限制序列化后的字符串长度为 65,536，并非严格的 64 KiB 字节上限。图片转发也有 1 MiB 积压检查。`controlReply` 的匹配处理位于上述普通请求检查之前；`controlPending` 保存请求编号与 resolve，没有同时记录该请求所属连接。发往观看端的控制消息和普通消息也不是共用同一个校验入口。

这证明入口间的检查并不一致，不代表已证明可被攻击或所有特殊消息都没有其他保护。

**建议的最小落点**：分别补协调消息、控制回包、普通事件的类型/大小/频率检查；pending 绑定预期连接，连接关闭时结束属于它的等待；统一发送积压及 pending 数量预算，超限只处理该成员。保留合法旧客户端的字段和消息格式，不直接套入会拒绝兼容字段的严格解码器。

**验收条件**：错误来源的回包不能完成另一连接的请求；大回包、连续回包、慢接收端不会无限积压；正常探测和移交仍可用，普通成员不受另一个慢成员拖累。

## 4. 播放判断：首帧证明、持续解码、手机前后台分开看

**Piik 的事实**：首帧观察优先使用视频帧回调，兼容分支检查帧计数或播放时间推进，并匹配预期媒体流；另有解码帧推进证明。播放期间使用独立停滞检测，15 秒没有解码进展时上报对应路线，主机暂停/网页挂起时暂停判断，前台恢复时重设基线；旧路线代次不得提交新结果。

**Roomcast 的事实**：已有首帧门禁，检查 loadeddata/canplay、readyState 和 videoWidth；已经在异步统计前后检查当前播放代次与候选。统计包含 framesDecoded，但本轮检查的 ScreenPlayer 没有把持续解码停滞作为独立异常检测。不能把“旧回调隔离”或“不把 ICE connected 当播放成功”说成待从零实现。

**建议的最小落点**：先只加观测和诊断，匹配当前流/当前候选，区分静止画面、主机暂停、手机后台、统计缺失和真正的解码停止；新帧证明可优先帧回调并保留兼容方式。确定判定可靠后，再复用现有恢复入口，单独验证只影响发生问题的观看端。不会因此新增媒体路线、调整 P2P/VDO/TURN 顺序或恢复策略。

**验收条件**：旧流回调不能把新流标为可播放；锁屏/切后台不会误触发恢复；静止桌面及浏览器不提供帧统计时不误判；已有画面之后真的停止解码能留下明确证据。15 秒只是 Piik 的实现值，需要结合 Roomcast 行为决定阈值。

## 5. 成员恢复：身份与本次连接分开

**Piik 的事实**：按房间和角色保存稳定 clientID；服务器为同一 clientID 复用逻辑 peerID，同时更换 sessionID；旧 session 的断开不能清掉新 session。断开清理宽限结束之后身份也会被删除，并非永久保留。

**Roomcast 的事实**：普通 `room:join` 使用当前本地桥接 socket.id 作为成员 ID。现有访客连接映射有旧清理不能删除新映射的保护；beta.7 也已能探测并清理失联成员，但刷新后重新入房没有上述跨连接身份恢复。这两种保护解决的是不同层面的事情。

**建议的最小落点**：完成鉴权后，签发限定本房间/本成员的恢复凭证，网页刷新能证明自己是原成员；恢复时替换该成员连接，新会话成为唯一有效会话。不能只提交可猜/可自填的 clientID，也不能按昵称去重；新设备应保持独立成员，存储不可用时安全退回新入房。复制标签页可能复制 sessionStorage，需要定义并验证冲突规则，不能承诺一个浏览器随机 ID 就能正确区分所有情况。

**验收条件**：刷新后短期内恢复为同一成员，旧连接迟到的 close 不删除新连接；同名不同设备保持两个成员；别人持有同一公共邀请也不能声称恢复任意既有成员。旧网页客户端继续正常加入。此项会涉及加入、踢人、移交及权限，应单独实现和提交，不混入小修。

## 6. 多人性能：先测，再考虑共享编码分组

Piik 可按观众预算分组，共用编码媒体源，独立关键帧后替换源而保留连接。Roomcast 已共享采集源，但当前向不同 PeerConnection 发送的编码成本不能仅靠源码推断；也不能断言它每位观众都重新采集。

可先测 1、3、5、9 名观众时的 CPU、GPU、上行和掉帧，找出瓶颈是否确在编码。只有测出编码瓶颈，才评估共享编码或受限质量分组。Piik 的 Go 媒体引擎不能直接塞进 Electron/WebRTC 链路；不引入中央转发服务、不改变中继使用方式。没有基准前不承诺性能提升百分比。

## 执行边界

- 当前结果是可行候选与验收标准，未把候选写成已完成或已测试。
- 实施时每项独立最小修改、可回滚提交、时间戳记录；依据修改范围安排相应回归，再构建。
- 不修改 TURN 取用/凭据/媒体车道，不新增中继不可用提示；不复制 Piik 的自动入房、退出等待链或整个服务端架构。
- Roomcast 已有 Electron 沙箱、IPC 来源/主帧验证、房间 HMAC 等边界，补强针对具体入口，不能据此断言整个项目不安全。
- 本轮未运行 Piik、Roomcast 或真机；跨网络连接根因、微信真实后台存活和多人编码实际成本仍待证据。
