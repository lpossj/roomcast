# Roomcast 当前短板审查

2026-09-27，基于当前 beta.7 源码和本地发布产物。范围：此前六项 Piik 候选之外的短板及网页入口可达性；只审查，没有改动应用、部署或发布。

## 最新用户反馈与结论边界

用户在本轮明确反馈“手机测过，没问题了”。据此记录当前手机实测通过，不再把“手机当前连不上”列为未解决故障。未提供设备/浏览器/网络矩阵，不把这句话扩展为全部移动环境均已验证，也不要求重复同一测试。

以下区分确定事实、设计限制和待验证推断，不能把源码审查写成故障已复现。

## 1. 网页观看入口只有一个默认托管站点

**事实**：默认邀请网页为 `https://lpossj.github.io/roomcast/`。它提供 HTML/JS/CSS 观看程序，不承载房主桌面服务或整个媒体传输。设备若首次访问时无法取得该站点页面或关键脚本，就无法正常使用这个网页入口；浏览器曾缓存不构成可靠备用入口。

`github.com` 仓库网站和 `lpossj.github.io` Pages 网站是不同域名，因此仅前者打不开不等于后者必然打不开。能打开网页之后，还需要邀请中使用的 PeerJS 信令、对应 VDO 信令以及媒体连接可达；“入口成功”不是全链路成功。

**设计限制**：给 GitHub Pages 绑定自有域名，托管仍在 GitHub Pages。根据 GitHub 官方的 CNAME/地址设置，这只是另一个访问名称；如果阻断在托管网络线路，不能保证改域名解决。这是基于其部署方式作出的判断，没有在用户手机模拟封锁。

**可行方向**：同一份静态观看页可部署到用户网络能够访问的 HTTPS 静态托管，默认邀请指向该入口，GitHub Pages 保留为备用。无需网页建房、中央媒体转发或改 TURN。桌面已有 `ROOMCAST_WEB_VIEWER_URL` 的入口配置能力；Vite 资源使用相对路径。具体托管可达性、证书、部署版本/协议同步和邀请解析需实施时验收。主站加载不了时主站内的“切备用”按钮也加载不了，因此备用链接应由仍能运行的桌面客户端生成。

证据：[默认入口](C:/Users/Administrator/Documents/ChatGPT/屏幕共享/electron/web-invite.cjs:6)、[桌面可配置入口](C:/Users/Administrator/Documents/ChatGPT/屏幕共享/electron/main.cjs:439)、[相对构建路径](C:/Users/Administrator/Documents/ChatGPT/屏幕共享/vite.config.js:25)；[GitHub Pages 说明](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages)、[自定义域名设置](https://docs.github.com/github/working-with-github-pages/managing-a-custom-domain-for-your-github-pages-site)。

## 2. 发布存在两个可能互相覆盖的入口

**事实**：Release workflow 由标签触发，重新构建后对同名附件执行 `gh release upload --clobber`。本地验证后手动上传与该流程并存。本次 beta.7 已通过取消它自己触发的重复流程避免覆盖，发布附件已核对一致；不是声称当前产物损坏。

**短板**：下次可能上传的是另一轮构建，测试证据和实际附件不易对应，还会重复消耗流量。应明确选用“CI 构建并发布”或“只发布已验证本地产物”的路径，公开后默认不覆盖二进制，以提交号和摘要关联验证结果。这个改动可独立于连接代码实施。

证据：[发布流程](C:/Users/Administrator/Documents/ChatGPT/屏幕共享/.github/workflows/release.yml:147)、[本次发布记录](C:/Users/Administrator/Documents/ChatGPT/屏幕共享/docs/时间戳记录/发布-beta7-20260927.md:10)。

## 3. 包装和检查门禁仍保留未使用的旧组件

**事实**：网页邀请生成器已不启动隧道，但 `package.json` 仍要求随包复制 `runtime/web-invite/cloudflared.exe`；beta.7 实际展开目录中该文件 55,254,472 字节，约 55 MB。构建流程会准备它，网络架构检查和 release verifier 仍要求它存在。

**短板**：旧依赖增加包体、准备时间、许可及维护成本。EXE 实际 149,916,100 字节，ZIP 221,714,201 字节。清除这一个未使用组件是具体候选，不等于压缩包能恰好减少 55 MB，也不能不经验证乱删 OBS DLL。

**可行方向**：独立核对引用后，同步去除打包项、获取步骤、过时门禁和校验要求；再验实际包的邀请、播放和退出。当前仅审查，没有删除组件或重打包。

## 4. 邀请访问权限不够细

**事实**：普通邀请凭据是房间级 inviteSecret；`member:kick` 标记并断开当前成员连接，没有同时撤销这份已分享邀请。未在本次定向审查的入房/鉴权链中看到独立的限时邀请或单份邀请撤销。

**设计限制**：踢出连接不等于撤销持有人已有的入房凭据；单独控制某一份外发邀请的能力有限。不能把它描述成不需要凭据即可入房的漏洞，也没有在本轮尝试重新加入或运行利用实验。

**可行方向**：若需要更细控制，单独设计邀请失效、房间停止接纳新成员或可撤销能力凭证；与恢复成员身份的目标区分，实施需兼容旧客户端并验证权限边界，不应混入退出小修。

证据：[房间邀请生成](C:/Users/Administrator/Documents/ChatGPT/屏幕共享/src/p2p.js:536)、[入房鉴权](C:/Users/Administrator/Documents/ChatGPT/屏幕共享/src/p2p.js:1776)、[踢人入口](C:/Users/Administrator/Documents/ChatGPT/屏幕共享/server/rooms.mjs:2811)。

## 5. 发布来源验证仍可加强

**事实**：当前 Windows 发布说明记录未签名，打包配置关闭签名；自动更新验证 Release 提供的 SHA256，缺少有效校验则不安装，已有路径、版本及归档保护。本轮检查的更新链没有独立发布签名验证。

**短板**：哈希验证擅长检查包与发布清单是否一致；它与独立可信签名提供的发布者身份验证用途不同。来源可信度主要依赖官方发布渠道，陌生用户的运行确认体验也较弱。不是声称已经被篡改或当前更新不校验。

**可行方向**：在需要扩大公开分发时评估代码签名与带签名的更新清单，设置明确的密钥与渠道管理。没有选定付费方案，没有购买或声称签名可消除所有系统告警。

证据：[打包签名设置](C:/Users/Administrator/Documents/ChatGPT/屏幕共享/package.json:170)、[更新摘要验证](C:/Users/Administrator/Documents/ChatGPT/屏幕共享/electron/update-check.mjs:323)、[Electron 签名说明](https://www.electronjs.org/docs/latest/tutorial/code-signing)。

## 7. 核心职责集中，回归覆盖仍需要针对真实场景积累

**事实**：当前 p2p.js 3,720 行、rooms.mjs 4,431 行，承担控制、成员、迁移、媒体会话等多种职责；App 和播放器也较集中。日常 CI 执行许可证、Node 测试、构建和网络门禁；Release 流程另有打包检查。本轮没有新增测试失败证据。

**判断**：职责多使改动影响范围和异常收尾更难判断，源码门禁也不能证明浏览器或系统的实际行为。行数本身不是代码质量结论。已有手机实测通过应保留为证据；长期运行、设备休眠/恢复、弱网与高负载缺少本轮新数据，不能推断“肯定有 bug”。

**可行方向**：以真实故障和常用操作补有意义的回归；修某处时才提取稳定的小边界，不做整体重写。不因测试数量增加而宣称覆盖所有场景，也不重复用户已通过的同一手机测试。

## 已知但按约束只记录：长房间的临时 TURN 凭据
