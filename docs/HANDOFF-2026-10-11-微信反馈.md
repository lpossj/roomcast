### 是否会让原本进得来的用户进不来

**有风险。原 IPv6/IPv4 ICE 候选仍然保留，但当前 EasyTier 并非完全独立、无影响的备用通道。**

- `src/p2p.js:662、826`：创建 EasyTier 房间或加入带 campus 的桌面邀请时，在 `openPeer()` 前必须成功 `await startCampusSession()`。提权被拒、驱动或组件启动失败、虚拟子网与本机地址冲突等会阻断普通入房；即使原 IPv6/IPv4 可以直连，也没有自动退回普通流程。
- `electron/main.cjs:30–47` 与 `electron/campus-policy.cjs`：校园会话期间对窗口 WebRTC 设置 UDP 50000–50255，作用包含物理 IPv6/IPv4 接口，不只是虚拟网卡。网络或防火墙对该端口段的限制可能影响原有连接。停止会话会恢复原策略，但结束事件同时触发房间断开。Electron API 语义参见 [官方 WebContents 说明](https://www.electronjs.org/docs/latest/api/web-contents#contentssetwebrtcudpportrangeudpportrange)。
- `src/campus-session.js:8–10`：收到组网结束事件就断开整个房间，没有检查当前房间/媒体是否仍通过物理接口正常工作。
- `src/ice-policy.js`：原 IPv6/IPv4 候选保留，另外追加虚拟 IPv4 候选。现有 IPv6 0ms、IPv4 450ms 的候选顺序仍在，但虚拟 IPv4 与普通 IPv4 未分成“普通失败后才启用”的两个阶段；不能保证普通路径成功时绝不选择 EasyTier。

配置没有开启出口代理、DNS 接管或默认出口路由，不能把上述问题描述为 EasyTier 必然替换系统所有 IPv6/IPv4 网络。实际风险来自入房前置依赖、窗口级端口策略及故障耦合；真实设备影响尚未实测。网页版邀请虽已删除 campus、不要求浏览器安装 EasyTier，但房主端的端口限制仍可能影响它，不能保证网页端不受影响。

### 视频共享能否走 EasyTier

**现有 WebRTC 屏幕视频及随附音频具备经 EasyTier 虚拟网卡传输的接入条件，但未证明实际成功。** 发布端 `src/p2p.js:2995、3013` 使用 `createRoomcastPeerConnection()` 并加入共享媒体轨道；观看端 `src/ScreenPlayer.jsx:969` 使用同一工厂。`src/ice-policy.js` / `src/campus-session.js` 为这些连接追加虚拟接口候选，虚拟子网 ACL 允许对应 UDP 端口。因此不仅房间消息，屏幕媒体也可以在 ICE 选中可达的虚拟候选对时走组网。

条件与边界：双方桌面端需要加入同一 EasyTier 虚拟网络，虚拟接口候选、绑定端口和 ACL 必须相符，且 ICE 成功选中该路径。EasyTier 自身可能打洞直连，也可能经公共节点中继，不能把“经 EasyTier”直接等同于“底层 P2P 打洞成功”。普通浏览器没有这里内置的虚拟网卡能力。PeerJS/VDO 等外部信令也没有自动迁入虚拟网，信令不可达不能仅靠媒体虚拟候选解决。TURN-only 路线仍使用原有 TURN 策略，没有改为 EasyTier。

特别注意：`src/ScreenPlayer.jsx:148、179` 的“校园互联”文字主要按 `campusSecret` 判断，而不是实际选中的 ICE 候选对。现有 `src/p2p-diagnostics.js` 虽读取候选对 RTT，但未记录足够的接口归属信息。**界面显示校园互联不等于视频已经走 EasyTier。** 本次不修改标签或诊断代码。
