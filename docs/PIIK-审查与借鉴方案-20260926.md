## 相同问题如何处理

| 问题 | Piik 源码中的做法 | Roomcast 的取舍 |
| --- | --- | --- |
| 同一网页收到新邀请 | `session.ts:456/493` 解析 `#v=`，监听 hashchange；App 按新凭证重建观看页 | 监听 hashchange/popstate，新网址优先于缓存；仅预填并显示加入确认，用户提交后才加入 |
| 网页没有发关闭事件 | 信令服务 30 秒 ping/pong；下一轮未响应时终止连接，统一执行成员断开 | 房主独立探测每个已入房成员，失联只释放该成员本地桥接，不依赖手机关页事件 |
| 重连被旧连接清理 | 稳定 clientID、逻辑 peerID 和本次 sessionID 分离；断开必须匹配当前 sessionID | 保留现有“成员映射仍指向该连接才删除”的保护并补回归；暂不新增跨页面稳定身份协议 |
| 停止卡住 | signaling.stop 同步关闭、代次隔离旧回调；采集 Close 在可能阻塞的停止命令前先安排强制取消 | 复用已有 AbortController 和操作代次；原有离开入口第一次直接强制清理，资源释放逐项隔离 |

Piik 的有效邀请会直接进入 ViewerPage 并启动信令，并不保证弹出手动加入界面。Roomcast 保留明确加入确认，避免仅解析网址就形成成员。

Piik 的 pagehide/隐藏处理主要暂停质量观测，并非每次都会 signal.stop；如果微信只是隐藏页面且连接还回答 Pong，源码不能证明它会立即删除成员。手机也可能遗漏 pagehide，独立存活清理因此必要。[MDN 的 pagehide 生命周期说明](https://developer.mozilla.org/en-US/docs/Web/API/Window/pagehide_event)。

## 本次选择落地

1. **动态邀请入口**：新邀请覆盖旧缓存，支持在输入框粘贴完整网页邀请；存储或历史 API 被禁用时仍保留当前邀请。新邀请切断尚未完成的入房操作，旧结果不能覆盖新状态。
2. **成员存活检查**：成功入房后每 10 秒使用既有只读 `migration:probe`，最多等待 15 秒；任何回复（包括 ok=false）均证明页面仍响应。没有回复才释放该成员桥接与连接。该探测不触发移交，也不改鉴权、TURN 或媒体协议，旧 beta.3 网页已支持它。正常调度下失联约 25 秒内被清理；房主自身计时停滞超过容忍范围则重新探测，不据此批量误删成员。暂停、休眠或极端网络延迟下不承诺精确清理时刻。
3. **第一次离开就结束当前操作**：已有离开入口调用强制清理；移除额外“停止连接/停止等待并离开”按钮。原有弹窗 ×、Escape 仍可取消卡住请求。用户主动离开会结束自己当前房间连接，不等待房主移交。
4. **独立资源释放**：一个发布器、轨道、Peer、桥接或本地服务关闭失败，不阻止其他资源关闭；保留已有 Windows X/Alt+F4 直接进程退出边界。JavaScript 资源释放无法解决主线程自身无限同步阻塞，原生窗口关闭负责桌面进程退出。

当前实现是借鉴机制后的独立代码，没有复制 Piik 源文件。Piik 为 MIT；以后若直接使用代码，应保留其许可及署名。

## 可学但暂不引入

| 候选 | 可学习点 | 本次不做的依据 |
| --- | --- | --- |
| 稳定身份和会话分离 | 防止刷新重复成员，避免旧会话踢掉新会话；身份必须绑定已验证的房间能力凭证，不能用昵称去重 | 会涉及邀请鉴权、成员加入和迁移协议；当前最小失联清理无需扩大协议 |
| 控制面的收紧 | Piik 本地控制绑定 127.0.0.1，验证 Host/Origin 和每实例随机令牌；严格字段解析、消息长度与写队列预算 | Roomcast 已有隔离沙箱、IPC 来源/主帧检查及房间 HMAC，不能声称目前没有安全边界；应按实际入口逐项审查后独立补强 |
| 媒体切换的准备与提交 | Piik 使用 revision/generation 保证旧切换无法提交；以已解码帧证明可播放 | Roomcast 已有媒体竞速和可播放门禁；本次不改竞争顺序和媒体线路，后续只补有证据的缺口 |
| 编码源分组与共享 | Piik 分组编码、独立关键帧切换和源替换，可减少重复编码及观看连接重建 | Go 媒体链与 Roomcast OBS/WebRTC/VDO 不同，移植需要单独性能与兼容实验 |
| 中央服务或观众转发 | 有统一连接权威及流量控制机会 | 增加服务器成本、依赖及信任边界，超出本次最小修复且可能改变用户禁止改动的媒体/中继方式 |
| Windows Job Objects | 为自己启动的采集/隧道子进程设置主进程关闭即终止 | 这是补充候选，不是从 Piik 中看到的实现；需先验证所属进程、嵌套作业与自动更新影响，本次不增加原生依赖。[Microsoft 文档](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects) |

Piik 的 Go 启动器 q/Ctrl+C 先取消 context，再等待服务收尾；名义 5 秒 context 不覆盖所有无条件等待和无 context 的 Close，不能据此证明它所有异常都能 5 秒退出。其 standalone 控制台错误后等待 Enter 是专门行为，也不适合 Roomcast 原生 ×。Roomcast 不搬入这条退出等待链。
