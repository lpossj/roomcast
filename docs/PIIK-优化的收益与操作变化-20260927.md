# Piik 借鉴方案的收益与操作变化

前面提出的六项是下一轮候选，目前尚未实施。以下描述实施目标和预期体验；已发布 beta.7 的行为在最后单独说明。

| 候选优化 | 具体收益与例子 | 用户操作会怎样变化 |
| --- | --- | --- |
| 停止操作统一时限 | 采集启动或停止卡住时，停止请求不必先等前面的操作和每个单独超时；停止后旧结果不能重新开启已取消的采集。只清理该操作所属进程 | 继续点击原有停止/离开一次；无需额外“强制停止”按钮。窗口 × 仍直接退出。整体停止预算尚未确定，需实施验证 |
| 故障阶段记录 | 手机出现失败时，记录能区分鉴权未完成、已入房但没首帧、采集或清理卡住；保留时间、版本和阶段，减少凭截图猜原因 | 日常加入、观看、退出不变。需要排查时可从设置导出本地诊断；记录不自动上传，排除邀请密钥等字段 |
| 控制消息与积压限制 | 错误回包不能完成其他连接的请求；异常频繁或慢接收端不会让等待和发送队列无界增长，其他成员继续正常使用 | 正常操作不变。超过明确限制时，只清理异常成员的连接，可能需要该成员重新加入，不让全房间承担影响 |
| 真实画面进展检测 | 连接显示正常却长时间没新画面时，能够留下对应媒体候选的证据；旧画面回调不能把新连接误判成可播放 | 第一阶段只观测记录，正常观看无需新增操作。后台/锁屏时暂停判断，返回前台重设基线。可靠后才单独考虑复用已有恢复入口，不在本方案中新增路线或承诺自动恢复 |
| 成员身份恢复 | 网页刷新或短暂重连后可恢复原成员，减少重复头像；旧连接迟到的断开不会踢掉新连接 | 仍保留手动加入确认。刷新后再次确认加入时，可恢复原身份；不改成打开链接即自动入房。不同设备和同名用户仍独立，复制标签页规则需单独设计；恢复凭证缺失/失效时正常新入房 |
| 多人共享编码分组 | 若编码确是多人观看的瓶颈，可减少重复编码并保留观看连接；目前未测得收益，不能承诺人数、耗电或帧率改善 | 计划先做性能实验，无用户操作变化。若实验支持实施，仍通过原有共享入口使用；质量分组及默认行为尚未确定 |

## beta.7 已发布的实际操作变化

- 网页打开新邀请会预填并显示加入确认，点击进入后才成为成员；在同一网页继续打开不同邀请也重新处理。
- 点击现有离开入口第一次就清理当前连接，不等待移交；创建/加入卡住时可用原弹窗 × 或 Escape 取消，再做其他操作。窗口右上角 ×/Alt+F4 保留直接退出行为。
- 没有响应的网页成员由房主独立探测并清理，正常调度下约 25 秒；不是承诺关网页的一刻立即从列表消失，后台仍响应的页面也不必然被判定为离线。
- 房主主动离开/关闭时不等待自动移交。希望其他人继续使用房间时，应先在成员管理完成主动移交。
- 只有桌面客户端能创建房间。手机网页供观看，具备屏幕采集能力的电脑网页可在加入后共享。

## 状态与边界

候选收益均为源码对照后的预期，未进行新功能实现或验证；beta.7 行为依据已发布说明与验收记录，微信/iOS 真机及跨网络结果仍未在本轮验证。所有候选保持 TURN 使用与媒体路线策略约束，分别最小实施、独立回滚和记录时间戳。
